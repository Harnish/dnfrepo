# apt/deb repos: own debs and Debian/Ubuntu mirrors

Status: draft for approval. Date: 2026-11-13.

## Intent

dnfrepo manages signed dnf repos. The author also runs Debian and Ubuntu machines and wants the same service to publish and mirror **apt** repos, so one tool, one UI, one set of access rules, pipelines and audit log covers both package worlds.

Two uses, kept separate:

1. **Own debs:** upload `.deb` files built in-house and publish them as their own suite, with dev → test → prod promotion like rpm repos.
2. **Mirrors:** a repo that is purely a mirror of an upstream apt suite (Debian, Ubuntu, or another dnfrepo), synced on a schedule with the same batches, filters and promotion as the rpm mirror, e.g. a local Debian/Ubuntu cache that is promoted dev → QA → prod.

## Goals

1. A repo has a **kind**, `rpm` or `deb`, chosen at creation and never changed. Everything not format-specific works for both kinds unchanged: access modes (public / ips / users), repo users, admin API and tokens, audit log, pipelines and promotion, retention, dedup, sources of the first stage, mirror schedules and batches, the admin UI.
2. A deb repo serves a standard apt archive at `/r/<slug>/`, so a client needs only:
   `deb [signed-by=/etc/apt/keyrings/dnfrepo.asc] https://<host>/r/<slug>/ <suite> <component>`
   The UI shows this line and the key setup, like it shows the `.repo` file for rpm repos.
3. **Own debs:** upload `.deb` to a first-stage deb repo; the package row is filled from the deb's control data. The repo is one suite (name chosen at creation, default the slug), one component (default `main`) and a list of architectures (default `amd64`, `arm64`). Architecture `all` packages appear in every architecture's index. An upload whose architecture is neither `all` nor in the repo's list is rejected.
4. **Mirrors:** create a deb mirror from an upstream archive URL plus suite, components and architectures. Same filters as the rpm mirror (name include/exclude patterns, latest N versions per (name, arch)), same schedule, Sync now, batches, batch promotion, credentials (sealed with `SECRET_KEY`) and optional upstream signature verification.
5. **Metadata is generated by dnfrepo** in pure Go (no apt tooling in the image) and signed with the existing instance GPG key: `Packages`, `Packages.gz`, `Release`, `Release.gpg` (detached) and `InRelease` (clearsigned). Mirrors also publish metadata signed by the instance key (they hold a filtered subset, so upstream metadata cannot be reused). Clients of a mirror use this instance's `/gpg.key`, as with rpm mirrors.
6. Retention and promotion order versions with **dpkg version comparison** (epoch, upstream, revision, `~` sorting).

## Non-goals (first version)

- Source packages (`deb-src`, `.dsc`), translations, `Contents` indexes, DEP-11/appstream, pdiffs, by-hash, udebs, `Packages.xz` output (gz only is enough; apt accepts it).
- Several suites in one repo, flat repos (`deb https://x/ ./`), mixing own debs into a mirrored suite.
- Per-package signature verification (only metadata is signed, as for rpm).
- Mirroring upstream deletions (a sync never deletes what the repo already has; retention purges).
- Changing a repo's kind after creation, converting rpm repos.
- Snapshots (frozen copies), already deferred for rpm.

## Anti-goals (a failure even if it technically works)

- Clients seeing a half-published archive: `Release` listing hashes for files that are missing or stale, or `Packages` listing a `.deb` that is not there. All of `dists/` is swapped atomically (generation directory plus symlink, like `repodata`), and `Release`, `Release.gpg`, `InRelease` always belong to the same generation.
- A mirror and own debs ever sharing a repo.
- A package entering a non-first stage other than by promotion; any write to package files outside `pipeline` under the per-repo mutex.
- The GPG private key or upstream credentials in logs, API responses or the DB in readable form (existing invariants).
- Per-kind code forking the existing rpm paths so that rpm behaviour changes. rpm repos must work exactly as before.
- A package accepted whose checksum or size differs from what the upstream metadata says.

## Constraints

- Go backend, PostgreSQL, existing `pipeline` as the only writer of package files. Numbered migrations (next is `009`), never edit applied ones. The existing invariants in `CLAUDE.md` stay true.
- The runtime image is `fedora-minimal:42` with `createrepo_c`; do not add apt tooling to it (`dpkg-scanpackages`, `reprepro`, `aptly`). Generate metadata in Go. Reading a `.deb` (ar archive, control tarball in gz/xz/zst) may use a small library or stdlib plus the compression libraries already in `go.mod`; adding a dependency needs a reason.
- Rebuild semantics match rpm: detached from request contexts, `REBUILD_TIMEOUT`, atomic swap, per-repo lock. A large mirror (Ubuntu main amd64 is ~60k packages) must rebuild in reasonable time: stream or reuse parsed control data instead of re-reading every `.deb` on each rebuild; store what the index needs in the DB at ingest.
- Tests: TDD, fake upstream via `httptest` (a small signed `InRelease` plus `Packages.gz` plus a couple of tiny debs generated in test code), no real network. A test must run real `apt`-style verification of the signature with the instance key (go-crypto is enough).

## Design (decisions by the author)

- Own debs and mirrors are separate repos; a deb mirror is exactly a mirror.
- The own-deb repo is its own suite.
- Same feature set and UI as rpm repos wherever it makes sense.

- **Promotion between stages:** each stage is its own repo with its own suite, components and arches; suite names need not match. A promotion is rejected, whole (all-or-nothing, as for rpm), if any selected package's component is not in the target's `components` or its architecture is neither `all` nor in the target's `arches`. (My call:) PATCH of `arches` on a deb repo only changes what future uploads and promotions accept and what is indexed; packages of a removed arch stay stored but are not indexed until the arch is re-added. Components are fixed at creation.
- **Sources:** GitHub release sources work for deb repos in v1: they pick `.deb` assets (matching the repo's architectures or `all`) instead of `.rpm`, name and version come from the deb's control data, and each picked asset enters through the same upload path. **Plex sources stay rpm-only** (409 on deb repos); the author only asked for GitHub `.deb`.

## Design (my calls, marked for review)

- **Arch `all`:** one row with `arch = all`; the index writer fans it out into every architecture's `Packages`. Retention and mirror "latest N" treat `all` as its own arch. A repo whose list is only `all`-capable is invalid: at least one real architecture is required.
- **Version columns:** `version` holds the full Debian version including epoch and revision; `release` is the empty string for deb rows (API and UI hide it). Versions differing only by epoch would collide on the epoch-less filename; accepted, upload fails with the existing "exists" error.
- **Filename versus control data:** control data is authoritative. An upload whose filename does not equal `<Package>_<version-without-epoch>_<Architecture>.deb` is rejected (400).
- **Control data stored:** the full control stanza verbatim for every package (mirrors: the upstream `Packages` stanza minus the fields dnfrepo rewrites, which are `Filename`, `Size` and the hashes; uploads: the stanza from the deb), so apt behaviour fields (Provides, Pre-Depends, Breaks, Multi-Arch, ...) survive. `md5` and `sha1` are computed from the file at ingest when not supplied, so `Packages` always carries MD5sum, SHA1 and SHA256.
- **Mirror signature verification:** the key is a pasted armored key (or a URL fetched once at save time, as `gpgkey` is for rpm) stored in the existing `gpg_key` column, with the existing `require_signature` flag. If a key is set, `InRelease` (or `Release` + `Release.gpg`) must carry a valid signature from at least one key in it; unset means no verification, as for rpm. `.repo` parsing is not used for deb.
- **`Release` freshness:** `Date` is the rebuild time; no `Valid-Until`, so a stalled mirror does not make clients fail.
- **Rollout:** migration `009` defaults every existing repo to `kind='rpm'`; rpm repos, routes and tests must behave byte-for-byte as before, so all deb code sits behind kind checks at the edges.

- **Data model:** `repos.kind text NOT NULL DEFAULT 'rpm'`. A `deb_repos` table (one row per deb repo): `suite`, `components text[]`, `arches text[]`. For an own-deb repo, `components` has one entry; a mirror may have several (matching upstream), and the mirror's suite/components/arches live there too. Package rows gain nullable `component`, and `deb_control` (the control fields needed to write the index: Depends, Description, Section, Priority, Maintainer, Installed-Size, etc., as text or jsonb) plus `md5`/`sha1` columns (nullable, deb only) because apt indexes need them. Existing `sha256`, `size`, `arch`, `name`, `version` are reused.
- **Filenames:** accept `name_version_arch.deb` where the version has no epoch (as Debian file names do). Row `version` holds the full version including epoch; the index `Filename:` is `pool/<component>/<filename>`. On disk the repo dir stays flat like rpm repos (one file per package, `<slug>/<filename>`), and the server maps `pool/<component>/<filename>` to it, so promotion, dedup, retention and orphan handling work unchanged.
- **Layout served:** `dists/<suite>/{Release,Release.gpg,InRelease}`, `dists/<suite>/<component>/binary-<arch>/{Packages,Packages.gz,Release}`, `pool/<component>/<filename>`. Only those paths are served; the existing access guard covers them.
- **Publisher:** `Publisher.Rebuild` dispatches on repo kind; the deb path writes a `dists.<gen>` directory and swaps the `dists` symlink, signs `Release` (detached) and writes `InRelease` (clearsigned), then prunes old generations. `Release` has `Origin`, `Label`, `Suite`, `Codename` (= suite), `Date`, `Architectures`, `Components`, `Description`, and MD5Sum/SHA1/SHA256 lists. The signer gains a clearsign method.
- **Mirror sync (deb):** fetch `dists/<suite>/InRelease` (fallback `Release` + `Release.gpg`); if a key is configured, verify, and fail the sync if it does not verify; for each wanted component/arch fetch the `Packages.xz` or `.gz` listed in `Release`, verify its hash from `Release`, parse, apply filters, plan, download from the upstream pool path with a SHA256 check against `Packages`, stage, and publish through `pipeline.IngestBatch` as one batch. Reuse the existing scheduler, credentials sealing, staging, size limits and batch tables; only the upstream reader and planner are deb-specific. Ubuntu's `-updates` and `-security` pockets are separate suites, therefore separate mirrors.
- **API:** `POST /api/repos` accepts `kind` (`rpm` default), and for `deb` `suite`, `components`, `arches`. `PATCH` may change arches and description of a deb repo (triggers a rebuild). Upload accepts `.deb` for deb repos and rejects the wrong extension for each kind (400). `PUT /api/repos/{slug}/mirror` takes `suite`, `components`, `arches` for deb repos; `.repo` parsing is rpm only.
- **UI:** the new-repo form gets a Kind choice and the deb fields; the repo page shows the `sources.list` line and key instructions instead of the `.repo` download; the Mirror panel switches fields by kind; package tables show component/arch. Help page, README and `docs/api.md` are updated.
- **Browse page and feed** for deb repos list packages the same way; the `<slug>.repo` route 404s for deb repos.
- **Key delivery:** `/gpg.key` is the armored key; the UI documents saving it as `/etc/apt/keyrings/dnfrepo.asc` (apt 2.4+ accepts armored keys) and, for older systems, `gpg --dearmor`.
